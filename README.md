# Git Trend Journal

GitHub Trending의 Today / Week / Month 상위 10개 프로젝트를 한국어 보고서로 자동 생성하는 GitHub Pages 블로그입니다. 프로젝트별 용도·활용 제안과 공식 README의 시작 절차를 함께 제공합니다. 유료 API, 서버, 외부 DB, npm 의존성이 없습니다.

## 실행

Node.js 22 이상(권장 24)만 필요합니다. `npm install`은 필요 없습니다.

```sh
node scripts/collect.mjs
node --test
node scripts/build.mjs
node scripts/serve.mjs
```

미리보기: http://127.0.0.1:4173

## 프로젝트 활용 분석

`scripts/usage.mjs`가 GitHub REST API에서 공개 README를 읽어 다음 내용을 생성합니다.

- **어디에 쓰나요:** 저장소 설명과 README 도입부의 키워드로 도구 유형을 분류합니다.
- **이런 분이 살펴보세요 / 활용 예:** 분류에 따른 한국어 해석·제안입니다. 실제 사용자 사례나 지원 기능을 추가 검증한 결과와 구분해 표시합니다.
- **시작 방법:** README의 Quick start / Getting started / Installation / Usage 절 제목, 하위 절 최대 3개, 짧은 원문 명령 블록 또는 문장 발췌를 제공합니다. 임의의 설치 명령을 생성하지 않습니다. 명령은 실행하지 않으며, 문서의 전체 절차 확인 링크를 제공합니다.
- **미확인 처리:** 용도 분류가 불확실하면 미확정으로, 문서가 없거나 호출 제한·네트워크 오류가 있으면 확인 대기로 표시합니다. README 실패가 트렌드 보고서 전체 발행을 막지는 않습니다. 다음 예약 실행에서 실패한 항목만 재시도합니다.

자동 생성은 규칙 기반이며 자유 형식 AI 분석이나 자동 번역이 아닙니다. 원문 발췌·절 제목·명령 예시는 원문 언어로 표시합니다. README에 실제로 사용한 사례가 있다고 주장하거나 해당 프로젝트가 동작한다고 보증하지 않습니다. 시작 절을 찾지 못하면 공식 README 링크를 제공합니다. 250KB 초과 문서는 자동 분석하지 않습니다.

원본 README는 저장하지 않고 추출한 정보, 원문 SHA, 확인 시각만 **최신 게시물의 프로젝트 항목**에 포함합니다. 기간별 중복 저장소는 실행 중 메모리에서 한 번만 조회합니다. 기존 게시물도 발행 키·발행 시각·장부 개수를 유지한 채 사용법을 보완하며, 이미 확인된 사용법은 새 보고서를 생성할 때 갱신합니다.

Actions에서는 기본 제공 `GITHUB_TOKEN`을 README 조회에만 추가로 사용하며, 별도 유료 키나 새 secret 등록은 필요 없습니다. 로컬에서는 토큰 없이 공개 README를 조회할 수 있고, 필요하면 기존 `GITHUB_TOKEN` 환경 변수를 사용할 수 있습니다. 인증값은 생성 JSON이나 로그에 저장하지 않습니다.

npm이 있으면 `npm run collect`, `npm run check`, `npm test`, `npm run build`, `npm run preview`도 사용할 수 있습니다. TypeScript를 사용하지 않으므로 별도 타입 검사나 ESLint는 없으며, Node 구문 검사와 동작 테스트로 검증합니다. 수동 환경 변수·토큰 설정은 필수가 아닙니다.

## GitHub Pages 설정

1. 이 폴더의 파일을 **공개 저장소의 루트**에 올립니다. 기본 브랜치는 `main`으로 설정합니다.
2. 저장소 Settings → Pages → Build and deployment → Source를 **GitHub Actions**로 선택합니다.
3. Actions에서 **트렌드 생성 및 Pages 발행**을 수동 실행합니다. 이후 매일 한국 시간 09:23 예약 실행됩니다.
4. 배포 주소는 `https://<아이디>.github.io/<저장소명>/`입니다. 모든 로컬 자산 경로는 상대 경로여서 프로젝트 Pages에서도 동작합니다.

공개 저장소와 표준 `ubuntu-latest` 러너를 사용합니다. 큰 러너, 유료 AI, 도메인 구매, 외부 호스팅은 사용하지 않습니다. Pages 배포 산출물 보관은 1일로 제한하며 별도 원본 아티팩트나 캐시를 만들지 않습니다. 무료 제공 범위와 이용 정책은 GitHub의 변경을 따릅니다.

## 발행과 중복 방지

- Today: 한국 날짜마다 한 번 처리합니다.
- Week: 한국 시간 월요일부터의 주를 키로 사용합니다. 처음 실행할 때와 새 주 첫 정상 실행 때 발행합니다.
- Month: 한국 연월을 키로 사용합니다. 처음 실행할 때와 새 달 첫 정상 실행 때 발행합니다.
- 본문의 실질 내용(프로젝트 순위·이름·설명·언어)이 과거 동일 기간 유형의 발행과 같으면 생략합니다. 숫자만 변한 경우에도 재발행하지 않습니다.
- 같은 프로젝트가 다른 기간에 등장하는 것은 정상입니다. Today와 Week를 서로 중복 처리하지 않습니다.
- 동일 기간 재실행은 수집도 생략합니다. 다음 기간에 내용이 달라지면 최신 글을 교체합니다.

`content/publication.json`에는 **최신 글 최대 3개와 발행 장부**만 있습니다. 별도 날짜별 스냅샷, 원본 HTML, 통계 이력, 과거 글 목록은 만들지 않습니다. 장부에는 기간 키, SHA-256 내용 해시, 처리 시각, 상태만 남깁니다. `published`는 보고서 생성 및 배포 대상을 준비했다는 뜻이며, 실제 공개 배포 성공은 Actions의 `deploy` 작업으로 확인합니다. 배포 실패 후 재실행해도 준비된 동일 보고서를 다시 배포하므로 글이 추가 생성되지 않습니다.

Git 저장소 특성상 변경 전 파일은 커밋 이력에 남습니다. 원본을 별도 누적 수집하지 않는다는 뜻이며, Git 이력까지 삭제하는 설계는 아닙니다. 장부는 중복 방지를 위해 계속 유지하며, 배포 파일에는 포함하지 않습니다.

## 분석 범위와 운영

목록과 스타 수는 GitHub Trending 웹 화면에서 수집합니다. 공식 Trending API를 사용한다고 주장하지 않습니다. GitHub 표시 순위를 그대로 유지하며, 그 목록 안에서 언어 분포와 표시 기간 스타 수를 비교합니다. GitHub가 사용하는 기간과 순위 선정 방식은 자체 달력 집계와 같다고 가정하지 않습니다. 인과 분석과 과거 대비 변화는 생성하지 않습니다. 외부 설명은 안전하게 텍스트로 표시하고 링크는 GitHub 주소로 제한합니다.

429·5xx·네트워크 오류는 최대 3회 시도합니다. 세 기간 중 수집이 필요한 작업이 하나라도 실패하면 새 파일을 저장하지 않아 기존 정상 글이 유지됩니다. 예약 실행은 지연될 수 있고, 공개 저장소가 60일 동안 활동이 없으면 예약 워크플로가 비활성화될 수 있습니다. 오류 시 Actions 로그를 확인하고 **Re-run jobs**로 재시도하세요. 장기간 같은 내용으로 커밋이 없다면 예약 활성화 상태도 확인해야 합니다.

GitHub 화면 구조가 바뀌면 파서 수정이 필요합니다. 파서가 프로젝트를 하나도 읽지 못하면 빈 글로 덮어쓰지 않고 실패합니다. 최초 수집 전에는 빈 상태를, 보고서 로딩 실패 시에는 재시도 버튼을 제공합니다. Google Fonts를 사용하며 연결되지 않으면 시스템 글꼴로 표시합니다.

## 설계 결정

Astro 등 프레임워크 대신 정적 HTML/CSS/JS와 Node 내장 기능을 사용했습니다. 화면 1개와 기간 탭 3개인 범위에서 설치·업데이트 의존성을 줄이고 무료 빌드를 단순하게 유지하기 위해서입니다. 자유 형식 AI 글 대신 수치 기반 한국어 템플릿을 사용해 API 비용과 근거 없는 성장 원인 생성을 방지합니다. 각 유형을 해당 기간에 한 번만 처리해 반복 게시를 줄였습니다.
